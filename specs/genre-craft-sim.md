# 手作模拟品类规范（craft-sim）

> 来源：`game-sushi`（2026-09-11 老板认可）。这一版把"为什么它被认可"拆成可验收的条目，
> 供同类游戏（寿司 / 烧烤 / 章鱼小丸子 / **饮品**）复用。
> 标 `[M]` = 机器可判（进 `h5-hard-rules.json`），标 `[H]` = 人审（进终审页勾选表）。

## 0. 品类定义

玩家扮演手艺人，按**固定顺序**完成 3–5 道工序，把原料变成一件**独一无二的成品**，
然后被打分。不是闯关、不是反应测试、没有 Game Over。

反例（本仓库里已有的、不属于本品类）：`belt-catch`（接）、`pan-whack`（砸）——
操作结束即消失，不留痕、不可回溯，所以只有分数没有作品。

---

## 1. 玩法：线性工序，一步一手势

| # | 条目 | 判法 |
|---|---|---|
| G1 | 工序 3–5 道，线性无分支，状态机可枚举 | `[M]` `state().phase` 取值集合 ≤5，且转移图无环无分支 |
| G2 | 每道工序只绑定一个手势，且手势与现实动作同构 | `[M]` 每个 phase 的指针事件处理只走一条分支；`[H]` 同构性人审 |
| G3 | 整局动词 ≤3 个（沿用现有 `ui.verbs` 预算） | `[M]` 已有 |
| G4 | 说明书只有一行 `hint`，无教程关、无弹窗说明 | `[M]` 每个 phase 有且只有一条 hint 文案 |
| G5 | 单局 60–150 秒 | `[M]` 机器人走完全流程墙钟落在区间内 |
| G6 | 订单/配方随机且不重复上一单 | `[M]` 连续 5 局订单名两两相邻不相等 |

手势与现实动作同构的意思（寿司的四条）：
涂抹=铺饭、点选=摆料、横拖=卷、点击=下刀。**不允许出现"按住蓄力""连点""摇一摇"这类
和现实动作无关的抽象操作。**

## 2. 成就感：成品必须能回溯到玩家的每一次输入

这是本品类最值钱的一条，也是"像游戏"和"像玩具"的分界。

| # | 条目 | 判法 |
|---|---|---|
| A1 | 存在一个**成品特征图**，其形态由玩家操作直接决定，而非预置贴图 | `[M]` 同一配方、两次不同操作，成品截图像素差 ≥ 阈值 |
| A2 | 成品特征图在**结算画面可见且是视觉主体** | `[H]` |
| A3 | 中间过程有一个**真的几何/物理关系**撑住可信度 | `[H]` 代码走查 |
| A4 | 玩家做的每一个动作都能被撤销或看到即时反馈 | `[M]` 每个可操作 phase 有 undo 或实时仪表 |

寿司的实现：`rollmath.js` 把海苔映射到阿基米德螺线，半径取 `r(θ) − y`，
所以铺在海苔上面的料卷完真的在里面；`pieces.js` 按配料的实际摆放位置换算极坐标现画横截面。
**切开看到的花纹是玩家自己摆出来的。**

> 做新品类时先回答一个问题：**"这一局的横截面是什么？"** 答不出来就别开工。
> 饮品的答案见 §7。

## 3. 分享欲：一局的产出是一张自带故事的图

| # | 条目 | 判法 |
|---|---|---|
| S1 | 结算画面同屏包含：成品 + 评级 + 分维度条 + 一句人话点评 | `[M]` DOM/state 结构检查 |
| S2 | 评级分 5 档（S/A/B/C/D 或等价），最低档不是失败 | `[M]` |
| S3 | 不存在 Game Over / 命数归零 / 重开局 | `[M]` `state().lives` 不存在，或永不减到 0 |
| S4 | 点评说人话：指出**具体哪一步怎么做会更好**，不是"评分 62" | `[M]` 每条 tip 含一个工序名 + 一个方向词；`[H]` 文案质量 |
| S5 | 满分有专属台词 | `[M]` |

寿司的点评样本：
`米饭铺得太少，海苔露白会卷不牢。` / `放了订单没要的配料，客人会疑惑。` /
`无可挑剔 —— 板前的手艺。`

## 4. 画面：先把光打对，素材是增量不是前提

`game-sushi` 一张 PNG 都没有（程序化贴图 + WebAudio 合成音效，全部 104KB），
老板仍然认可画面。结论：**可信度来自光影关系和材质参数，不来自图片分辨率。**

| # | 条目 | 判法 |
|---|---|---|
| V1 | 暗背景 + 雾，主体靠光从背景里"捞"出来 | `[M]` 背景亮度 < 0.15，主体区域平均亮度 / 背景亮度 ≥ 3 |
| V2 | 三灯以上：暖主光（带软阴影）+ 冷侧补光 + 轮廓光 | `[M]` 灯光数量与色温差；`[H]` 效果 |
| V3 | ACES tone mapping + sRGB 输出 + 环境反射（PMREM） | `[M]` 代码检查 |
| V4 | 相机在工序间自动补间，玩家从不需要操作镜头 | `[M]` 无 OrbitControls，且 phase 切换伴随 camera 位移 |
| V5 | 结尾有装盘/成品演出（位移 + 落定音效），高潮在最后 | `[M]` 最后一个 phase 有 ≥0.5s 的非交互动画 |
| V6 | UI 与 3D 场景分层：固定三处（订单/进度/操作条），互不遮挡 | `[M]` 已有 layout 检查可扩展 |
| V7 | 画面无方形暗块/亮块、无残影、无占位色块 | `[M]` 沿用 realism checklist |

## 5. 完成度 = 没有断头路

定义：**玩家能做的每个动作都有反馈，不合法的动作被提前挡住。**

| # | 条目 | 判法 |
|---|---|---|
| C1 | 非法状态下"下一步"按钮 disabled，而不是点了没反应或报错 | `[M]` |
| C2 | 每个可操作工序有撤销 | `[M]` |
| C3 | 有实时仪表（进度/数量/质量），且标出理想值刻度 | `[M]` |
| C4 | 操作越界当场提示（"太快了！会松散"），不静默 | `[M]` 越界输入后 1 帧内 hint 文本变化 |
| C5 | 竖屏按宽高比自动拉远机位，主体始终完整在画面内 | `[M]` 390×844 与 1620×861 下主体包围盒都在视口内 |
| C6 | 0 console error / 0 page error / 启动 ≤3s | `[M]` 已有 |

## 6. 工程约束（本仓库）

- 禁外链（`h5-hard-rules.json.static.forbid_patterns` 含 `https?://`）→ **three.js 必须 vendored**，
  不能学 `game-sushi` 用 CDN importmap。
- 总包 ≤ 4MB；竖屏 9:16 写死；`fake_dpr=3` 下跑 390×844。
- `game.js` 不得直接 `from 'three'`、不得碰 `rt.scene/renderer/camera`（`runtime_forbid_patterns`）。
  → **新的视觉能力要加在 `vendor/bf-runtime.js` 里，以 `rt.*` API 暴露**，不是每个游戏各写一遍。

## 7. 饮品分厂：液体怎么做

### 7.1 先定"横截面"

饮品的成品特征图 = **杯子的侧视分层**。
玩家倒的顺序、速度、分量 → 杯中液体的层次、边界清晰度、颜色过渡。
这同时满足 §2 的三条：物理可见、可回溯到输入、截图即成品。

对应的评分维度（替换寿司的米饭/配料/紧实/刀工）：
**配方符合度 / 分层清晰度 / 液位准确度 / 出品速度或拉花**。

### 7.2 原则：不做流体模拟，做"液体的 5 个可辨识特征"

人眼判断"这是液体"靠的是下面 5 条，不是 Navier-Stokes。
**任何一条缺失，再贵的模拟也会被看穿；五条齐全，最便宜的实现也成立。**

| # | 特征 | 最便宜的正确实现 |
|---|---|---|
| L1 | **弯液面亮边**（meniscus） | 液面圆盘边缘 3–5% 半径处一圈 fresnel 亮边，沿径向渐变 |
| L2 | **按厚度吸收的颜色**（Beer–Lambert） | 片元里 `exp(-absorb·thickness)`，圆柱厚度可解析求得；**不要用 transmission**（每个杯子一张 render target，移动端 fill rate 直接炸） |
| L3 | **晃动时的接触线跟着倾斜** | 液面 = 可倾斜平面，倾角由杯子加速度驱动的二阶弹簧阻尼系统给；杯壁圆柱用 clipping plane 或 shader 里 `discard y > plane(x,z)`。**只让顶面歪、接触线不动，一眼假** |
| L4 | **流柱随下落变细** | 质量守恒 + 重力：`r(y) = r0·(v0/v(y))^0.5`。TubeGeometry / 圆锥即可，配沿流向滚动的噪声 UV + 边缘亮边 |
| L5 | **落点涟漪 + 少量飞溅** | 从落点向外扩散的 ring 波，振幅衰减；飞溅用 ≤20 个 InstancedMesh 小球 |

### 7.3 分层的数据结构（核心机制）

液体不是一个颜色，是一个**按高度的 1D 浓度数组**（建议 64 段），传成 64×1 纹理，
液柱 shader 按 y 采样。

- 倒入时按**密度**决定沉降方向：糖浆密度高 → 往下钻；奶泡密度低 → 浮上去。
- 层与层的边界带一个"混合度"参数：倒得越快越猛，边界越浑浊。
  **这个参数就是"分层清晰度"评分的直接来源。**
- 搅拌 = 对数组做邻域平均，搅几下就浑，不可逆。

### 7.4 悬浮物（冰块 / 珍珠 / 气泡 / 果粒）

一律 `InstancedMesh`，不用粒子系统。

- 气泡：位置用 GPU 端时间函数沿 y 上升，到液面消失，CPU 不逐帧更新实例。
- 冰块：浮力只需"y clamp 到液面附近 + 轻微晃动"，不要真物理。
- 珍珠：杯底预设堆叠位置 + 随机抖动 + 掉落补间。

### 7.5 奶泡与拉花

液面上盖一层不透明、带噪声法线的圆盘，边缘不规则。
拉花直接画在这张 canvas 纹理上 —— 又一个"玩家输入 → 可见成品"的入口，
是饮品分厂第二个可选的"横截面"。

### 7.6 音效（成本极低，效果极高）

注入音的**基频随液位升高而升高**（真实的瓶子装水声学现象）。
几乎没有小游戏做这个，一做就非常"对"。用 `audio.js` 的 `noise()` 加一个随液位移动的带通即可。

### 7.7 运行时缺口（必须先补）

`vendor/bf-runtime.js` 目前是 **OrthographicCamera + 贴图 Plane 的 2D 精灵引擎**，
接不住上面任何一条。而 `game.js` 又被禁止直接碰 three。

→ 先给运行时加 3D 模式与液体组件（暂定 `rt.liquid(...)`、`rt.pour(...)`、`rt.vessel(...)`），
液体的正确性（L1–L5）由运行时一处保证、由判官一处验证，不散落在各游戏里。
这正是 `gaps.md` D1 那条"真实感返工的根因在引擎"的收口方向。

## 8. 镜头与动画规范（老板指定：要 `game-sushi` 那种感觉）

> 这一节全部是从 `game-sushi` 源码里量出来的**具体数字**，不是形容词。
> 手感 = 这些参数，照抄即可复现；改动要有理由。

### 8.1 镜头感：一工序一机位，镜头看玩家此刻要做的事

`game-sushi` 的五个机位（`game.js` VIEWS），FOV 恒定 **42°**：

| 工序 | 相机位置 | 注视点 | 用意 |
|---|---|---|---|
| prep 铺饭 | `0.6, 7.4, 8.4` | `0.1, 0.35, 0` | 高俯视，看全张海苔 |
| fill 加料 | `-2.6, 4.9, 6.6` | `-2.3, 0.35, 0` | **压低 + 左移**，贴近配料带 |
| roll 卷 | `3.0, 5.6, 9.0` | `1.2, 0.7, 0` | 右移拉远，给卷留出空间 |
| cut 切 | `9.6, 5.2, 5.2` | `0, 0.7, 0.1` | **大幅侧移到刀这一侧**，看刀落下 |
| serve 装盘 | `0, 8.4, W/2+11` | `0, 0.2, W/2+4.5` | 正俯视，成品照 |

三条可复制的规律：

- **C1｜每个机位有自己的注视点，对准此刻要操作的东西**，不是场景中心。
  `fill` 的注视点是配料带（`x=-2.3`）而不是整张海苔。
  镜头在**关注玩家的动作**，不是在展示场景 —— 这是镜头感的第一性原理。
- **C2｜机位高度是一条呼吸曲线**：`7.4 → 4.9 → 5.6 → 5.2 → 8.4`。
  中段最低（最亲密），结尾最高（最完整）。不要五个机位一样高。
- **C3｜竖屏自适应用 dolly，不用 zoom**：
  ```js
  k = clamp(1.78 / aspect, 1, 2.3)
  pos = (pos − tgt) · k + tgt        // 沿视线后退
  fog.near = 22k;  fog.far = 46k     // 雾距同步，背景衰减一致
  ```
  **FOV 恒定不改**。改 FOV 会让物体透视形变，一眼廉价。

补间：`dur = 0.85s`，`smoothstep(t) = t²(3−2t)`，**位置与注视点同时 lerp 再 lookAt**。
0.85 是关键值 —— 低于 0.6 显得慌，高于 1.2 显得拖。两头都缓、无 overshoot，
专业感来自"稳"不是"弹"。

`[M]` 判据：无 OrbitControls；每次 phase 切换伴随 camera 位移；每个 phase 的注视点互不相同；FOV 全程常量。

### 8.2 动画感：全部补间，没有一处线性

`game-sushi` 的动画时长表（照抄）：

| 动画 | 时长 | 曲线 | 附加手法 |
|---|---|---|---|
| 相机 | 0.85s | smoothstep | pos + target 同时补 |
| 竹帘摊开（收口） | 0.75s | `1 − smooth(k)` | 反向播放同一进度量 |
| 成品滑到中间 | 0.70s | smoothstep | `rotation.z = sin(kπ)·0.06` |
| 下刀 | 0.26s | **45% 下 / 55% 上** | 非对称 |
| 装盘每块 | 0.62s | smoothstep | `t = −i·0.09` 错峰 + `y += sin(kπ)·1.5` + `rotation.x: π/2→0` + 随机 spin ±0.25 |
| 高亮带呼吸 | — | `sin(t/420)` | opacity 0.3 ± 0.12 |
| 刀待机悬停 | — | `sin(t/260)·0.05` | 待机不静止 |

**五个通用手法**（这才是可复制的部分，与题材无关）：

- **A1｜错峰 stagger**：`t = −i·0.09`。一个参数把"一堆东西移动"变成"一串动作"。
- **A2｜抛物线弧**：任何 A→B 位移都加一行 `y += sin(kπ)·h`。
  从"滑过去"变成"被拿过去"。
- **A3｜途中摆动回正**：`rotation.z = sin(kπ)·0.06`。去了又回，暗示重量与惯性。
- **A4｜非对称时长**：下刀 45/55。**加速方向永远比恢复方向快。**
- **A5｜待机不静止**：刀悬停微浮、高亮带呼吸。画面里永远有东西在动，才"活着"。

`[M]` 判据：代码中不得出现未经 easing 的裸线性插值（`lerp(a,b,t)` 的 t 必须过 smooth 或等价曲线）；每个 A→B 位移动画必须含弧线项；多物件同步位移必须有 stagger。

### 8.3 画面感：零素材的配方

`game-sushi` 一张 PNG 都没有，全部 104KB。

**布光四件套**（`scene.js`）：
```
HemisphereLight(暖天 0xffe9c8 / 暗地 0x241a12, 0.55)
DirectionalLight(暖白 0xfff1d6, 2.5) 主光 · castShadow · 2048 · bias −0.0006
DirectionalLight(冷蓝 0xcfe0ff, 0.85) 侧补光      ← 冷暖对冲，层次的来源
SpotLight(暖橙 0xffd9a0, 26, penumbra 0.55) 顶部轮廓光
+ ACESFilmicToneMapping, exposure 1.06, SRGBColorSpace, PCFSoftShadowMap
+ 背景 0x1d1712 + Fog(同色, 22, 46)
```

**最省的一招**：`envTexture()` —— 一张 512×256 canvas 渐变（暖顶 → 中灰 → 暗地）
加两块亮灯箱，走 PMREM 做环境反射，`environmentIntensity = 0.55`。
**没有它，金属渲染成纯黑。** 5 行 canvas 换全场金属与瓷器的反射。

**程序化材质的统一公式**：底色 + 上千个低 alpha 随机小矩形 + 若干条正弦扰动的线。
木纹 / 砧板 / 海苔 / 盘子全是它，只换颜色与密度。全局 `memo()` 缓存，不重复生成。

**每个材质认真给 roughness / metalness**：
刀刃 `0.05 / 0.95`、刀身 `0.16 / 0.9`、盘子 `0.22 / 0.06`、**酱油 `0.08 / 0.4`**。
酱油那个 metalness 0.4 就是液体反射感的来源 —— 饮品分厂直接继承。

### 8.4 饮品分厂的机位表（按 §8.1 的规律推）

| 工序 | 机位特征 | 为什么 |
|---|---|---|
| 选杯 | 高俯视、略远 | 看全台面与杯型 |
| 加冰/基底 | 中高俯视，注视点=杯口 | 看东西落进去 |
| **倒入** | **低角度、近乎水平、贴近杯身** | **流柱的美在侧面；液面上升要看得见** |
| 搅拌/摇壶 | 中角度 + 轻微手持抖动 | 动作有力量 |
| 分层检视 | **侧视，从杯底缓慢上摇到杯口** | **这是饮品的"切开那一刀"** |
| 出品 | 正侧偏高，杯子缓慢自转（12s/圈）+ 暗角加深 | 成品照 |

倒入那一步是饮品**比寿司更强**的镜头时刻：寿司的高潮在结尾切开，
饮品的高潮可以有两次 —— 倒入时的流柱，和结束时的分层上摇。

### 8.5 饮品分厂的动画表

| 动画 | 时长 | 手法 |
|---|---|---|
| 起流 | 0.15s | 流柱半径 0→1，带一点过冲 |
| **断流** | 0.25s | 流柱**自上而下**消失，**末尾留一滴**。这一滴是真实感的签名 |
| 液位上升 | 跟随倒入量 | **不可线性**：液面有超调后阻尼回落 |
| 晃动 | ~1.5s 衰完 | 二阶弹簧阻尼，`ω≈9 rad/s`、`ζ≈0.18`（3–4 次可见振荡） |
| 冰块入杯 | 0.5s | 抛物线（A2）+ 随机自旋 + **入水下沉超调再浮起** + 涟漪 |
| 多块冰/珍珠 | — | 错峰 `−i·0.09`（A1） |
| 摇壶 | — | 非对称快慢（A4）+ 镜头轻微跟随 |
| 待机 | — | 液面永远有极微幅晃动、气泡上升（A5） |

## 9. 验收工具：`factory/craft_grade.py`（2026-09-11 起）

同一个模型给自己打分不收敛（bbq-skewer 视觉评审 12 轮全是 3/5），所以本品类的宏观验收改为**外部模型盲测**：

```bash
.venv/bin/python factory/craft_grade.py --cand game-drink --ref game-sushi   # 默认 gpt-5.4 + gemini-3.1-pro，各判 2 遍
```

- 无头浏览器把参考与候选各驾驭一遍（工序帧 + 镜头过渡中间帧 + 结算），随机贴 A/B 标签，判官不知道哪个是参考。
- 8 个宏观维度各 1–10：gameplay / achievement / share / polish / visuals / camera / animation / material。
- 判官除了给绝对分，还要给**两两比较**（每维"候选比参考好多少"，−3…+3）。绝对分噪声太大（同一组图 Gemini 两次能差 3–6 分），两两比较稳得多。
- `GRADE: PASS` = 穿模 0 处，且每维两两比较均值 ≥ −0.5（不比参考差），且 material 绝对均值 ≥ 4.5。默认每家判 3 遍（6 个样本）。
- 候选用固定的展示配方（`--recipe`，默认取工序最全的那杯：bar=朗姆日出，teashop=草莓奶盖），否则抽到"不加冰"这类单，第一道工序前后帧一样，判官会当成"没发生"。
- 产物：`<cand>/grade-latest-<theme>.md/json`、`grade-log.jsonl`、`grade/<ts>-<theme>/*.png`。
- 候选需支持 `?harness=1` + `window.__advance(sec)` / `__render()` 手动推进（软渲染下真折射只有 ~3fps，实时截图会失真）。

## 10. 硬性条件（2026-09-11 用户看过 game-drink 首版后加入）

| # | 条目 | 判法 |
|---|---|---|
| H1 | **不许穿模** | `[M]` 游戏暴露 `__game.checkClipping()`，打分器每个工序点调用，返回非空 = FAIL。查：固体两两不重叠、不碰壁不穿底；装饰整体在内壁内；果片用带切口的几何体卡在杯壁中心线；瓶身不进杯口 |
| H2 | **纯 HTML5 交付** | `[M]` 本地 http 直接跑，three 走 `vendor/`，无外链；不用 claude 网页展示 |
| H3 | **不指示、隐形评分** | `[M]` 界面里不出现目标线/光环/目标百分比/建议顺序；订单只有配料名（打乱）、分量档、装饰名。`[H]` 结算点评必须把隐形标准用人话说出来（"这杯要少冰（1–2 块），你放了 4 块"） |
| H4 | **主题明确到一家店** | `[H]` 调酒 = 酒吧，奶茶 = 奶茶铺；场景、器皿、配料、固体、装饰、UI 配色一套跟着主题走，`?theme=` 切换即另一款游戏 |
| H5 | **陈设写实** | `[H]` 几何体勾形 + 贴图/凹凸，不放光溜溜的原色几何体 |

| H6 | **手机屏幕大小** | `[M]` 游戏装在居中 9:16 容器（宽 = min(100vw, 56.25vh)），桌面两侧留黑；容器宽高比落在 0.44–0.6 |
| H7 | **工序跟主题走** | `[H]` 奶茶铺多一道「摇匀」：扣盖、按住左右甩、液体混匀并起细泡；要摇的配方订单里说明，奶盖/分层类摇了扣分 |

分量档 → 评分区间：冰 去冰 0 / 少冰 1–2 / 正常冰 3–4 / 多冰 5–6 块；珍珠 不加 0 / 少 1 / 正常 2 / 多 3 勺。

## 11. 五家新店（2026-09-14）：新机制清单与验收

引擎不变，主题表 `game-drink/src/themes.js` 决定一家店；每家至少一道别家没有的工序：

| 店 | 新机制 | 隐形评分 | 判据实现 |
|---|---|---|---|
| 咖啡馆 | 萃取（按住出浓缩） / 拉花（拖奶缸在 crema 上画） | 萃取量区间；图案与模板（心/叶/郁金香）重合度 | 液面画布 256² 与模板 IoU 式打分（`artScore`） |
| 居酒屋 | 挤柠檬（点一下一下）/ 搅拌（画圈） | 酸度档（挤几下）；搅几圈 + 气泡保留 | 圈数累计角度；每圈 fizz −0.13 |
| 茶馆 | 出汤时机 | 汤色（游戏内秒数）落在浓/淡窗口 | `retint()` 随时间向茶色演化；茶叶先浮 6s 再沉 |
| 刨冰摊 | 刨冰（按住长高）/ 淋酱（拖瓶淋色） | 冰山高度档；每种糖浆覆盖率 ≥ 12% | 蛋形圆锥网格 + 顶点色；`coverage(id)` |
| 果昔吧 | 打匀（按住起漩涡） | 细腻度（打多久）落在粗/细窗口 | 果块 `blend()` 缩小旋转；液体 `mix()` + 向果色 `retint()` |

打分器 `craft_grade.py --theme <id>` 通用驾驭每道工序（start → mid → done 三帧），穿模检查照旧。**注意串行跑**：并行会抢 CPU，寿司参考是实时录制，会超时。
